Detailed Description

HAL-side inventory of every component the Flux HAL pulls in.

The HAL knows which drivers and utility libraries it links against; higher layers (middleware / application) intentionally do not look across that boundary. This header exposes a stable read-only view that consumers can iterate without learning the HAL's internal submodule layout:

for (const auto& e : flux_version::GetHalManifest()) { printf("%s %s (%s)\n", e.name, e.version, e.git_sha); }

Entries cover:

  • the HAL itself ("hf-hal-flux-v1")
  • hf-core / hf-core-drivers / hf-core-utils aggregator repos
  • every external driver actually compiled into this image (per the HF_CORE_ENABLE_* feature flags)
  • internal helpers (hf-internal-interface-wrap, hf-pincfg)
  • utility libs (hf-utils-canopen / -general / -rtos-wrap)

Version strings come from each component's <x>_version.h (which defines HF_<X>_VERSION_STRING). Components without a version pattern report "n/a". Git short-SHAs come from flux_hal_git_manifest.h, written at HAL configure time against the actual checked-out HEAD of each submodule (so the SHA reflects what landed in the firmware image, not a stale parent pointer).

Add-on consumer pattern

When external board code uses a HAL handler base class (CommManager / GpioManager / AdcManager) plus its own off-board driver, that handler is the right place to publish its driver's row. The HAL never touches it; the consumer concatenates its own entries on top of GetHalManifest() for display.
